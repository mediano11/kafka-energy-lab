## МЕТА РОБОТИ

Змоделювати систему моніторингу для 1000 (було зроблено 2000) малих генераторів (сонячних, вітрових, біоенергетичних) з використанням Apache Cassandra та проаналізувати вплив схеми партиціонування на продуктивність системи.

## 1. СТРУКТУРА БАЗИ ДАНИХ

### 1.1 Keyspace

```sql
CREATE KEYSPACE der_monitoring
WITH REPLICATION = {
    'class': 'SimpleStrategy',
    'replication_factor': 1
};
```

### 1.2 Таблиця 1: Оперативні дані генераторів

```sql
CREATE TABLE generator_operational_data (
    generator_id UUID,
    timestamp TIMESTAMP,
    power_output DOUBLE,
    voltage DOUBLE,
    current DOUBLE,
    temperature DOUBLE,
    wind_speed DOUBLE,
    solar_irradiance DOUBLE,
    efficiency DOUBLE,
    status TEXT,
    PRIMARY KEY (generator_id, timestamp)
) WITH CLUSTERING ORDER BY (timestamp DESC);
```

**Призначення:** Миттєві показання сенсорів генераторів  
**Partition key:** `generator_id` (для рівномірного розподілу)  
**Clustering key:** `timestamp` (хронологічне впорядкування)

### 1.3 Таблиця 2: Метадані генераторів

```sql
CREATE TABLE generator_sources (
    generator_id UUID,
    source_type TEXT,
    region TEXT,
    capacity DOUBLE,
    installation_date TIMESTAMP,
    manufacturer TEXT,
    model TEXT,
    coordinates TEXT,
    PRIMARY KEY (generator_id, source_type)
);
```

**Призначення:** Метадані про типи джерел енергії  
**Partition key:** `generator_id`  
**Clustering key:** `source_type`

### 1.4 Таблиця 3: Регіональні баланси

```sql
CREATE TABLE regional_energy_balance (
    region TEXT,
    date DATE,
    total_generation DOUBLE,
    total_consumption DOUBLE,
    net_balance DOUBLE,
    peak_demand DOUBLE,
    renewable_percentage DOUBLE,
    grid_stability_index DOUBLE,
    PRIMARY KEY (region, date)
) WITH CLUSTERING ORDER BY (date DESC);
```

**Призначення:** Добові баланси енергії по регіонах  
**Partition key:** `region` (регіональний розподіл)  
**Clustering key:** `date` (хронологічне впорядкування)

### 1.5 Таблиця 4: Звіти диспетчера

```sql
CREATE TABLE dispatcher_reports (
    report_type TEXT,
    report_date TIMESTAMP,
    region TEXT,
    total_generators INT,
    total_capacity DOUBLE,
    average_efficiency DOUBLE,
    peak_generation DOUBLE,
    system_reliability DOUBLE,
    maintenance_alerts INT,
    performance_score DOUBLE,
    PRIMARY KEY (report_type, report_date)
) WITH CLUSTERING ORDER BY (report_date DESC);
```

**Призначення:** Агреговані звіти для центрального диспетчера  
**Partition key:** `report_type` (розподіл по типах звітів)  
**Clustering key:** `report_date` (хронологічне впорядкування)

## 5. ВИСНОВКИ ЩОДО ЕФЕКТИВНОСТІ CASSANDRA ДЛЯ ЕНЕРГЕТИЧНИХ IoT-СИСТЕМ

### 5.1 Переваги Cassandra для IoT-систем

#### 5.1.1 Відмінна продуктивність для оперативних запитів

- **Partition key запити:** 4.26мс - відмінна швидкість
- **Масштабованість:** 504,600 записів обробляються ефективно
- **Висока пропускна здатність:** 1.85мс на вставку

#### 5.1.2 Оптимальна структура для часових рядів

- **Хронологічне впорядкування:** `timestamp DESC` забезпечує швидкий доступ до останніх даних
- **Ефективне зберігання:** Оптимальна структура для IoT-сенсорів
- **Швидкий доступ:** Partition key забезпечує O(1) доступ до даних генератора

#### 5.1.3 Відмінний баланс партицій

- **Регіональний розподіл:** CV = 6.59% - відмінний баланс
- **Розподіл по типах:** CV = 1.81% - ідеальний баланс
- **Рівномірність:** Всі регіони мають приблизно однакову кількість генераторів

### 5.2 обмеження та проблеми

#### 5.2.1 Повільні JOIN запити

- **Region JOIN:** 7.8x повільніше за partition key
- **Source type JOIN:** 7.8x повільніше за partition key
- **Аналітичні запити:** До 546.9x повільніше

#### 5.2.2 Проблеми з великими таблицями

- **generator_operational_data:** 4.44с для COUNT(\*) - неприйнятно повільно
- **Масштабування:** Проблеми з ростом обсягу даних
- **Пам'ять:** Високе споживання пам'яті для великих таблиць

#### 5.2.3 Обмеження CQL

- **Відсутність JOIN:** Потребує додаткових запитів
- **Складні аналітичні запити:** Обмежені можливості
- **ALLOW FILTERING:** Критично повільний

### 5.3 Рекомендації по оптимізації

#### 5.3.1 Оптимізація запитів

- **Використовувати partition key** для оперативних запитів
- **Створити додаткові таблиці** для аналітичних потреб
- **Batch операції** для масових вставок
- **Підготовлені запити** для повторюваних операцій

#### 5.3.2 Архітектурні рішення

- **Гібридна схема:** Різні partition keys для різних типів запитів
- **Денормалізація:** Дублювання даних для швидкого доступу
- **Кешування:** Redis для часто використовуваних запитів
- **Розділення:** Різні таблиці для різних часових періодів

### 5.4 Підсумкова оцінка

| Критерій                 | Оцінка     | Коментар                                |
| ------------------------ | ---------- | --------------------------------------- |
| **Оперативні запити**    | ⭐⭐⭐⭐⭐ | Partition key забезпечує швидкий доступ |
| **Аналітичні запити**    | ⭐⭐       | JOIN запити повільні                    |
| **Масштабованість**      | ⭐⭐⭐     | Проблеми з великими таблицями           |
| **Баланс партицій**      | ⭐⭐⭐⭐⭐ | Ідеальний розподіл                      |
| **Зберігання IoT-даних** | ⭐⭐⭐⭐⭐ | Оптимальна структура                    |
| **Загальна оцінка**      | ⭐⭐⭐⭐   | Підходить для IoT, потребує оптимізації |

### 5.5 Висновки

**Cassandra відмінно підходить для енергетичних IoT-систем** завдяки:

- Швидкому доступу до оперативних даних
- Відмінному балансу партицій
- Ефективному зберіганню часових рядів
- Високій масштабованості

**Однак потребує оптимізації** для:

- Аналітичних запитів
- Великих обсягів даних
- Складних JOIN операцій
