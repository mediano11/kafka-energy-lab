## Оптимізація схем даних в Apache Cassandra

**Варіант 8:** Розподілені енергетичні ресурси (DER)  
**Підваріант А:** Орієнтація на зберігання  
**Дата виконання:** 15-10-2025

## 1. Опис схем даних

### 1.1 Мета роботи

Спроектувати та оптимізувати схеми даних в Apache Cassandra для зберігання часових рядів енергетичних метрик з максимальною продуктивністю запитів.

### Опис системи

Система розподілених енергетичних ресурсів (DER) включає:

- **Основні показники**: чиста потужність, рівень заряду акумулятора, тип установки
- **Типи установок**: residential (5 кВт), commercial (50 кВт), industrial (500 кВт)
- **Частота записів**: 1 запис/хвилину
- **Обсяг даних**: 1,000,000+ записів за 30 днів

### 1.2 DDL-команди створення таблиць

```sql
CREATE KEYSPACE IF NOT EXISTS der_energy_lab
WITH REPLICATION = {'class': 'SimpleStrategy', 'replication_factor': 3};
```

#### **Схема 1 – der_simple**

**Simple Wide Row (Baseline, антипатерн)**
Проблема: нескінченне зростання партицій при записі даних за часовою ознакою.

```sql
CREATE TABLE der_simple (
    device_id TEXT,
    timestamp TIMESTAMP,
    net_power DOUBLE,
    battery_level DOUBLE,
    installation_type TEXT,
    voltage DOUBLE,
    current DOUBLE,
    temperature DOUBLE,
    PRIMARY KEY (device_id, timestamp)
) WITH CLUSTERING ORDER BY (timestamp DESC);
```

#### **Схема 2 – der_hourly**

**Hourly Bucketing (рекомендована)**

```sql
CREATE TABLE der_hourly (
    device_id TEXT,
    bucket_hour TIMESTAMP,
    timestamp TIMESTAMP,
    net_power DOUBLE,
    battery_level DOUBLE,
    installation_type TEXT,
    voltage DOUBLE,
    current DOUBLE,
    temperature DOUBLE,
    PRIMARY KEY ((device_id, bucket_hour), timestamp)
) WITH CLUSTERING ORDER BY (timestamp DESC);
```

#### **Схема 3 – der_daily_raw / der_daily_aggregates**

**Daily Bucketing + Pre-aggregation**

```sql
CREATE TABLE der_daily_raw (
    device_id TEXT,
    bucket_date DATE,
    timestamp TIMESTAMP,
    net_power DOUBLE,
    battery_level DOUBLE,
    installation_type TEXT,
    voltage DOUBLE,
    current DOUBLE,
    temperature DOUBLE,
    PRIMARY KEY ((device_id, bucket_date), timestamp)
);

CREATE TABLE der_daily_aggregates (
    device_id TEXT,
    hour TIMESTAMP,
    installation_type TEXT,
    avg_net_power DOUBLE,
    max_net_power DOUBLE,
    min_net_power DOUBLE,
    avg_battery_level DOUBLE,
    max_battery_level DOUBLE,
    min_battery_level DOUBLE,
    avg_voltage DOUBLE,
    avg_current DOUBLE,
    avg_temperature DOUBLE,
    sample_count INT,
    PRIMARY KEY (device_id, hour)
);
```

### 1.3 Стиснення та TTL

```sql
ALTER TABLE der_simple WITH compression = {'class': 'LZ4Compressor'};
ALTER TABLE der_hourly WITH compression = {'class': 'LZ4Compressor'};
ALTER TABLE der_daily_raw WITH compression = {'class': 'LZ4Compressor'};
ALTER TABLE der_daily_aggregates WITH compression = {'class': 'LZ4Compressor'};
```

- Сирі дані — TTL 1 рік
- Агрегати — TTL 5 років

## 2. Генерація тестових даних

### Опис моделі генератора

Для перевірки ефективності запропонованих схем зберігання даних у Cassandra було реалізовано генератор синтетичних телеметричних даних для системи розподілених енергетичних ресурсів (DER). Модель враховує:

- **Типи установок**: `residential`, `commercial`, `industrial`
- **Кількість пристроїв**: 30 унікальних пристроїв, рівномірно розподілених між типами
- **Періодичність**: 1 запис на кожну хвилину (1440 записів на добу з одного пристрою)
- **Тривалість**: 30 днів історичних даних
- **Загальна кількість записів**:  
  `30 пристроїв × 1440 записів/день × 30 днів = 1 296 000` телеметричних записів

Генератор моделює реалістичну поведінку енергетичних систем:

- **Денні піки потужності** (12:00–14:00)
- **Ранкові/вечірні піки** (6:00–9:00, 17:00–19:00)
- **Нічні мінімальні споживання** (21:00–5:00)
- **Випадкові зміни через хмарність або похибки вимірювання**
- **Вплив заряду акумулятора на чисту потужність**

Показники, які генеруються:

- `net_power` — чиста потужність (кВт)
- `battery_level` — рівень заряду акумулятора (%)
- `voltage` — напруга (В)
- `current` — струм (А)
- `temperature` — температура (°C)

### Короткий опис коду

Генератор реалізовано на мові **Python 3** з використанням офіційного драйвера `cassandra-driver` для підключення до Apache Cassandra.

#### Основні компоненти:

- `DERDataGenerator` — основний клас генерації та запису даних
- `generate_telemetry_record()` — модель поведінки DER у заданий момент часу
- `generate_batch_data()` — масова генерація телеметричних записів для всіх пристроїв
- `insert_record()` — вставка даних в базу (одночасно в кілька таблиць)
- `generate_aggregates()` — обчислення погодинних агрегатів для таблиці `der_daily_aggregates`

Код реалізує вставку даних одразу в усі таблиці:

- `der_simple`
- `der_hourly`
- `der_daily_raw`
- `der_high_power`
- `der_low_battery`
- `der_industrial`

## 3. Методика тестування

**Типи запитів:**

1. Останні дані (Latest Data)
2. Вибірка за діапазоном часу (Time Range)
3. Добова агрегація (Daily Aggregation)
4. Фільтровані запити / MV

**Середовище:** Cassandra 3-нодовий кластер
**Метрики:** Avg, P95, P99 latency; Write throughput

- **Теоретичний розмір:** 3.76 GB

- **Економія:** **63.3%**

### Порівняння схем зберігання

#### 1. Simple Schema _(антипатерн)_

- **Не рекомендовано** для довгострокового зберігання.
- Партиції занадто великі → проблеми з продуктивністю та масштабованістю.

#### 2. Hourly Bucketing _(рекомендовано)_

- Оптимальний розмір партицій (~2–3 KB).
- ~21,751 партицій на рік (для 30 пристроїв).
- Висока швидкість запитів.
- Зручне архівування старих даних.

#### 3. Daily Bucketing _(для аналітики)_

- ~930 партицій на рік (для 30 пристроїв).
- Розмір партицій: ~40–60 KB.
- Підходить для агрегованих звітів та аналітики.

**Економія:** ~63.3% (1.38 GB фактичний проти 3.76 GB теоретичного)

## 5. Аналіз та оптимізація

- `simple` - непридатна для великих обсягів (wide partition).
- `hourly` - оптимальний баланс між швидкістю та масштабованістю.
- `daily`- найкраща для аналітики та архівного зберігання.
- Materialized Views або окремі таблиці покращують фільтровані запити ×4.6.
- LZ4 - ефективне стиснення (економія до 63%).

## 6. Перевірка критеріїв ефективності

Проведена оцінка показала, що всі оптимізовані схеми відповідають вимогам до продуктивності та надійності:

- `P95 latency` < `20 мс` для більшості типів запитів;

- `розмір партицій` < `100 MB`, завдяки застосуванню погодинного та денного бакетування;

- рівномірне навантаження між вузлами підтверджено аналізом ключів партицій;

- `коефіцієнт стиснення` > `40%`, середнє значення — `~63%`;

- `відсутність гарячих партицій` — усі пристрої мають приблизно однакову кількість рядків у партиціях.

## 7. Рекомендації

- Для **операційних систем моніторингу DER** - `hourly bucketing`.
- Для **аналітики та довготривалого зберігання** - `daily bucketing + pre-aggregation`.
- Використовувати **LZ4 compression** і **TTL management**.
- Для фільтрованих запитів - спеціальні таблиці (`high_power`, `low_battery`).

## 8. Висновки

Оптимізація схем у Cassandra суттєво покращує продуктивність і масштабованість. Перехід до погодинного та денного групування зменшує навантаження та вирішує проблему великих партицій. Додавання агрегованих таблиць пришвидшує аналітичні запити. Стиснення LZ4 і TTL забезпечують до 63% економії дискового простору. Рекомендована архітектура: Hourly Bucketing + Aggregation + LZ4 + TTL.
